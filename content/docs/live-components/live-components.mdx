title: "Live Components"
---

Live Components are reusable UI elements that combine **Python logic** with a **PyBlade template**. Unlike regular PyBlade components, they can respond to user interactions and update their content without requiring a full page reload.

If you already know how PyBlade components work, Live Components should feel familiar. They are rendered using the same component syntax you have already seen. The main difference is what happens behind the scenes when PyBlade finds the component.

<Callout type="info" title={"PyBlade Components vs. Live Components"}>

Regular PyBlade components are reusable pieces of HTML that are rendered when the page is generated.

Live Components can do everything regular components can do, but they can also respond to interactions and update themselves dynamically without requiring a full page reload.

In simple terms:

* Regular component: reusable UI.
* Live Component: reusable UI + Python behavior + live updates.

</Callout>

## Creating a Live Component

A Live Component consists of two parts:

* A **Python class** that inherits from `LiveComponent` and contains the component's logic.
* A **PyBlade template** that defines what the component looks like.

PyBlade CLI provides a command to generate both files for you:

```bash
pyblade make:livecomponent TodoList
```

You can also use *kebab-case* names:

```bash
pyblade make:livecomponent todo-list
```
Or even *snake_case*:

```bash
pyblade make:livecomponent todo_list
```

By default, PyBlade creates the component inside its own folder:

```files
components
└── todo_list
    ├── todo_list.py
    └── todo_list.html
```

The Python file contains the Live Component class:

```python title="components/todo_list/todo_list.py"
from pyblade import LiveComponent

class TodoList(LiveComponent):

    def render(self):
        return self.render_template(context={})
```

And the HTML file contains its PyBlade template:

```html title="components/todo_list/todo_list.html"
<div>
    {# Your component content goes here #}
</div>
```

You can also create these files manually if you prefer.

<Callout type="info" title={"Naming convention"}>
Generated files and folders use *snake_case*, while component classes use *PascalCase*.

For example, a component named `TodoList` is generated as `todo_list`, while its Python class remains `TodoList`.
</Callout>

## Understanding component folders

You may notice that the Python class and template are placed inside a folder with the same name as the component.

This folder is only there to keep the component's files organized. It is not part of the component's name.

For example:

```files
components
└── todo_list
    ├── todo_list.py
    └── todo_list.html
```

The component is still simply called `todo-list`.

You therefore render it as:

```html
<pb-todo-list />
```

You do not need to include the folder name when rendering the component.

This organization is intentionally abstract. PyBlade uses the folder to keep the component's files together, while the component itself is identified by its name.

### Flat components

If you prefer not to create a separate folder for every Live Component, you can use the `--flat` option:

```bash
pyblade make:livecomponent TodoList --flat
```

The generated files will then be placed directly inside the components directory:

```files
components
├── todo_list.py
├── todo_list.html
└── ...
```

You can also configure this behavior in your `pyblade.toml` file, so you don't have to specify `--flat` every time.

This is simply an organizational choice. It does not change how you render the component.

## Inline components

If a component is small enough, you can keep its template directly inside the Python class instead of creating a separate HTML file.

These are called **inline components**.

For example:

```python title="components/todo_list/todo_list.py"
from pyblade import LiveComponent

class TodoList(LiveComponent):

    def render(self):
        return self.render_inline("""
            <div>
                {# Your content goes here #}
            </div>
        """)
```

You can generate an inline component using the `--inline` option:

```bash
pyblade make:livecomponent TodoList --inline
```

An inline component still requires its Python class. Only the separate template file is omitted.

## Omitting the `render` method

If your component follows PyBlade's conventional naming structure, you can omit the `render` method entirely.

PyBlade Live will automatically use the template associated with the component:

```python title="components/todo_list/todo_list.py"
from pyblade import LiveComponent

class TodoList(LiveComponent):
    ...
```

With the conventional structure:

```files
components
└── todo_list
    ├── todo_list.py
    └── todo_list.html
```

PyBlade automatically knows that `todo_list.html` belongs to the `TodoList` component.

If you use a different template name or location, you can customize the template resolution. For a fixed template, override the `template_name` property with the template path:

```python
class TodoList(LiveComponent):
    template_name = "path.to.template"
```

For more advanced or dynamic template resolution, you can instead override the `get_template_name()` method.

```python
class TodoList(LiveComponent):

    def get_template_name(self):
        return "path.to.template"
```


This lets you keep simple components concise while still giving you full control over which template a component renders.

## Rendering Live Components

Live Components use the **same syntax as regular PyBlade components**.

The preferred way to render the `TodoList` component is with a component tag:

```html
<pb-todo-list />
```

You can also use the `@component` directive:

```html
@component("todo-list")
```

Both forms refer to the same component.

The tag syntax is generally easier to read when your component is part of the HTML structure, while the `@component` directive can be useful when you need to render a component dynamically or use it in a template expression.

<Callout type="info" title={"The same syntax is used for regular and Live Components"}>

You don't need a special syntax to tell PyBlade that a component is live.
PyBlade determines which type of component to render when it searches for the component.
</Callout>

### How PyBlade finds a component

Because regular and Live Components use the same syntax, you may wonder how PyBlade knows which one to render.

When PyBlade encounters a component such as:

```html
<pb-card />
```

it searches for a **Live Component first**.

In this case, PyBlade looks for the Python class that defines the `card` Live Component. If it finds it, PyBlade renders the Live Component.

If no Live Component is found, PyBlade then searches for a regular PyBlade component named `card`.

If neither a Live Component nor a regular component can be found, PyBlade raises the `ComponentNotFound` exception indicating that the component could not be resolved.

The process can be summarized as:

```text
<pb-card />
     │
     ▼
Look for a Live Component
     │
     ├── Found ──► Render Live Component
     │
     └── Not found
             │
             ▼
      Look for regular component
             │
             ├── Found ──► Render regular component
             │
             └── Not found ──► Raise an exception
```

This behavior allows you to use the same component syntax throughout your templates without having to remember whether a component is regular or live.


<Callout type="info" title="Component names must be unique within a component directory.">

You cannot have two regular components with the same name, two Live Components with the same name, or a regular component and a Live Component with the same name in the same directory.

PyBlade also enforces this rule when generating components. If the generated file names would conflict with an existing component, the command returns an error instead of overwriting the existing files.

Components with the same name can only coexist when they are placed in separate component directories.

</Callout>


### Component names

Component tags use the component's **kebab-case name**:

```html
<pb-todo-list />
```

For a Python class named:

```python
class TodoList(LiveComponent):
    ...
```

the corresponding component name is `todo-list`.

You can also use the `@component` directive with the same name:

```html
@component("todo-list")
```

Do not use the Python class name directly in the component tag:

```html
<pb-TodoList />
```

Component names should use **kebab-case** or the supported **snake_case** form.

## Passing data to components

Live Components can receive initial data from the template when they are rendered.

You can pass a value using a regular attribute:

```html
<pb-todo-list title="My Tasks" />
```

If you need to pass a Python value or variable, use a bound attribute by prefixing the attribute name with `:` like this:

```html
<pb-todo-list :title="initial_title" />
```

When using the `@component` directive, you can pass a dictionary containing the data as the second argument:

```html
@component("todo-list", {"title": initial_title})
```

The values in the dictionary are passed to the Live Component in the same way as values passed through a component tag.


<Callout type="info" title="Already familiar?">

If you have already read the [Passing data to components](/components#passing-data-to-components) section for regular PyBlade components, the syntax here works in the same way.

The difference is what the Live Component does with the received data.

</Callout>

### Receiving data in the component

Data passed to a Live Component is received through its `mount()` method.

The `mount()` method is the Live Component equivalent of Python's `__init__()` method. It is used to receive and/or initialize the data passed to the component when it is created.

For example:


```python title="components/todo_list/todo_list.py"
from pyblade import LiveComponent


class TodoList(LiveComponent):

    def mount(self, title: str):
        self.title = title

    def render(self):
        return self.render_template(context={})
```

When the component is rendered as:

```html
<pb-todo-list title="My Tasks" />
```

PyBlade calls `mount()` during the component's initial creation and passes `"My Tasks"` as the `title` argument.

You can think of `mount()` as the place where you prepare a Live Component when it is first created. It is similar in purpose to a Python class constructor, although it follows the Live Component lifecycle rather than replacing `__init__()`.

We will explore `mount()` and the other lifecycle hooks in the [Lifecycle hooks](lifecycle-hooks) section.

### Automatically assigning component properties

For simple cases, you can omit `mount()` entirely.

If you explicitly declare a typed property whose name matches a value passed to the component, PyBlade Live can assign the value automatically:

```python title="components/todo_list/todo_list.py"
from pyblade import LiveComponent


class TodoList(LiveComponent):

    title: str

    def render(self):
        return self.render_template(context={})
```

You can then render the component as:

```html
<pb-todo-list title="My Tasks" />
```

PyBlade will automatically assign the value to the `title` property.

This is equivalent to assigning the property yourself inside `mount()` for this simple case.


## Rendering components in loops

When rendering elements inside a loop in a Live Component template, PyBlade needs a way to distinguish one item from another when the list changes.

For this reason, elements rendered by a loop should have a **unique `key`**.

For example:

```html title="components/todo_list/todo_list.html"
<div>
    @for (task in tasks)
        <div key="{{ task.id }}">
            {# ... #}
        </div>
    @endfor
</div>
```

The `key` should uniquely identify each item. Using the item's database ID is often a good choice.

The same principle applies when rendering Live Components inside a loop.

You can pass the key directly to a component tag:

```html title="templates/todo.html"
<div>
    @for (task in tasks)
        <pb-task-item :task="task" :key="task.id" />
    @endfor
</div>
```

When using the `@component` directive, the key can be provided as a separate argument:

```html title="templates/todo.html"
<div>
    @for (task in tasks)
        @component(
            "task-item",
            {"task": task},
            key=task.id
        )
    @endfor
</div>
```

<Callout type="info" title={"Why do I need a key?"}>

When a list changes, PyBlade Live needs to know which rendered element corresponds to which item.

A unique `key` gives each item an identity, allowing PyBlade to correctly match the existing elements with the new ones.

You will see this become especially important when building lists that can be added to, removed from, filtered, or reordered.

</Callout>

## Full-page components

A full-page component allows a Live Component to be assigned directly to a route instead of being rendered inside another PyBlade template.

This is particularly useful when an entire page naturally belongs to a single Live Component, such as a dashboard, task list, profile page, or form.

Full-page components also work especially well with PyBlade's SPA-style navigation using `pb:navigate`, allowing users to move between full-page components without a complete browser page reload.

### Defining a full-page component

Full-page components can be assigned directly to a route using `as_view()`.

<Tabs groupId="framework" items={["Django", "Flask"]}>
    <Tab>
        ```python title="urls.py"
        from django.urls import path

        from components.todo_list import TodoList

        urlpatterns = [
            path("tasks/", TodoList.as_view()),
        ]
        ```
    </Tab>

    <Tab>
        ```python title="app.py"
        from flask import Flask

        from components.todo_list import TodoList

        app = Flask(__name__)

        app.add_url_rule(
            "/tasks/",
            view_func=TodoList.as_view(),
        )
        ```
    </Tab>
</Tabs>

When the user visits `/tasks/`, the `TodoList` component is rendered as the page itself rather than being placed inside another PyBlade template.

### The application layout

Full-page components rendered through routes use your application's layout by default.

PyBlade looks for an application layout at:

```text
templates/
└── layouts/
    └── app.html
```

If this file does not exist, you can generate it with:

```bash
pyblade make:layout app
```

Your application layout should contain a `{{ slot }}` placeholder where the full-page component's content will be rendered:

```html title="templates/layouts/app.html"
<!DOCTYPE html>
<html lang="@lang">
<head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">

    <title>{{ title }}</title>
    
    @pbstyles
    @stack('styles')
</head>

<body>
    {{ slot }}

    @pbscripts
    @stack('scripts')
</body>
</html>
```

The layout is responsible for the common structure of your application, while the full-page component provides the content for the current page. The two `@stack` directives are where components send the stylesheets and scripts they need: see [Scripts and styles](#scripts-and-styles).

You can customize the default application layout in your `pyblade.toml` file. This is useful when your application has a different layout structure, for example:

```toml
[live_component]
layout = "layouts.page"
```

With this configuration, full-page components will use `templates/layouts/page.html` instead of `templates/layouts/app.html`.

### Component-specific layouts

Sometimes a particular full-page component needs a different layout from the application's default layout. For example, a dashboard may use a different navigation structure from a public-facing page.

You can specify a layout directly on the component by overriding its `layout` property:

```python
from pyblade import LiveComponent


class Dashboard(LiveComponent):
    layout = "layouts.dashboard"
```

The `Dashboard` component will then use `templates/layouts/dashboard.html` instead of the default application layout.

You can also use the `@layout` decorator:

```python
from pyblade import LiveComponent
from pyblade.decorators import layout


@layout("layouts.dashboard")
class Dashboard(LiveComponent):
    ...
```

For more advanced cases, you can override the `get_layout()` method to determine the layout dynamically:

```python
from pyblade import LiveComponent


class Dashboard(LiveComponent):

    def get_layout(self):
        if self.user.is_admin:
            return "layouts.admin"

        return "layouts.dashboard"
```

### Navigating between full-page components

Full-page components are especially useful when combined with the `pb:navigate` attribute.

For example, your application layout might contain:

```html
<nav>
    <a href="/tasks/" pb:navigate>Tasks</a>
    <a href="/profile/" pb:navigate>Profile</a>
    <a href="/settings/" pb:navigate>Settings</a>
</nav>

@pbscripts
```

When a user clicks one of these links, PyBlade intercepts the navigation and loads the destination page without performing a full browser reload.

Behind the scenes, PyBlade requests the destination URL, processes the response, and updates the appropriate part of the current page while keeping the application layout in place. A progress bar is displayed during the navigation to provide visual feedback.

The browser URL and history are also updated, so the navigation behaves like normal browser navigation. Users can still use the Back and Forward buttons as expected.

### Page metadata

SPA-style navigation does not prevent each page from having its own metadata.

When navigating to a new page with `pb:navigate`, PyBlade updates the page title to the destination page's `<title>`, and adds the stylesheets and scripts of its `<head>` that the current page doesn't have yet. Other `<meta>` elements are left as they were on the first page loaded.

Every page is still a server-rendered URL: loading it directly, or letting a search engine crawl it, gives the complete page with its own metadata. This keeps full-page components suitable for SEO-friendly applications.

### Accessing route parameters

Full-page components can also receive parameters from the URL.

For example:

<Tabs groupId="framework" items={["Django", "Flask"]}>

    <Tab>

    ```python title="urls.py"
    urlpatterns = [
        path("tasks/<int:id>/", TaskDetail.as_view()),
    ]
    ```

    </Tab>

    <Tab>

    ```python name="routes.py"
    app.add_url_rule(
        "/tasks/<int:id>/",
        view_func=TaskDetail.as_view(),
    )
    ```

    </Tab>

</Tabs>

The `id` parameter can then be received by the component's `mount()` method:

```python title="components/task_detail/task_detail.py"
from pyblade import LiveComponent
from app.models import Task


class TaskDetail(LiveComponent):

    def mount(self, id: int):
        self.task = Task.objects.get(id=id)

    def render(self):
        return self.render_template()
```

If the user visits `/tasks/1/`, the value `1` is passed to the component as the `id` parameter.

This makes full-page components convenient for pages that depend on route parameters, such as `/tasks/<id>/`, `/users/<id>/`, or `/products/<slug>/`.

## Scripts and styles

A component often needs more than its markup: a library loaded on the page, a stylesheet, or a few lines of JavaScript of its own. PyBlade gives you two directives for that. `@push` sends markup to a place in the layout, and `@script` runs JavaScript that belongs to the component.

### Pushing to the layout

Some markup is needed by a component but belongs elsewhere on the page. A chart component needs its charting library loaded, yet the `<script>` tag should be at the end of the `<body>`, not in the middle of the component.

The layout names those places with `@stack`, as in the [application layout](#the-application-layout) above:

```html title="templates/layouts/app.html"
<head>
    @pbstyles
    @stack('styles') <!-- [!code highlight] -->
</head>

<body>
    {{ slot }}

    @pbscripts
    @stack('scripts') <!-- [!code highlight] -->
</body>
```

A component then sends markup to a stack with `@push` and `@endpush`:

```html title="components/sales_chart.html"
<div>
    <canvas></canvas>
</div>

@push('scripts')
<script src="https://cdn.jsdelivr.net/npm/chart.js"></script>
@endpush
```

When the page is rendered, the `<script>` tag comes out where `@stack('scripts')` is, at the end of the `<body>`. Pushed content comes out in the order it was pushed, so push a library before the code that uses it.

You can push from any template rendered on the page: the page itself, a partial brought in with `@include`, a regular component or a live component, however deeply nested. A push inside an `@if` whose condition is false is not made, and content pushed to a stack the layout doesn't have goes nowhere. The name of a stack may be any expression: `@stack(name)` and `@push(name)` work with a variable too.

A `@push` block may be written after the component's root element, as above. Its content is rendered in the stack, not in the component, so it doesn't count against the single root element a component must have.

#### Pushed content is kept once

The same content is never added to a stack twice. If the `sales_chart` component above is used three times on a page, Chart.js is still loaded **once**:

```html
<pb-sales-chart />
<pb-sales-chart />
<pb-sales-chart />
```

Two pushes count as the same when their rendered content is the same, ignoring the whitespace around it.

<Callout type="info" title={"Coming from Laravel?"}>
PyBlade's `@push` behaves like Laravel's `@pushOnce`. There is no separate `@pushOnce` directive: loading the same script twice on a page is almost never what you want.
</Callout>

#### Pushing after an action

A live component can also push when it renders again after an action. Say a component only shows a map once the user asks for it:

```python title="components/store_locator/store_locator.py"
from pyblade import LiveComponent

class StoreLocator(LiveComponent):
    map_shown: bool = False

    def show_map(self):
        self.map_shown = True
```

```html title="components/store_locator/store_locator.html"
<div>
    <button pb:click="show_map">Show the map</button>

    @if(map_shown)
        <div id="map"></div>

        @push('scripts')
        <script src="/static/js/maps.js"></script>
        @endpush
    @endif
</div>
```

The component is rendered again without the layout around it, so there is no stack for the script to land in. PyBlade sends what the component pushed along with its new markup, and adds to the page's `scripts` stack whatever the page doesn't hold yet. The script is added once and runs, however many times the button is clicked.

Pushes also follow the user across pages: see [Navigation](/live-components/features/navigation#pushed-content).

### Running JavaScript with `@script`

A plain `<script>` tag inside a live component is rendered like the rest of its markup, but the browser only runs it when the page loads. When the component updates after an action, the new markup is put in place without running any script in it, and the script has no way to reach its component.

Write the component's JavaScript between `@script` and `@endscript` instead, usually after the root element:

```python title="components/counter/counter.py"
from pyblade import LiveComponent

class Counter(LiveComponent):
    count: int = 0

    def increment(self):
        self.count += 1
```

```html title="components/counter/counter.html"
<div>
    <h1>{{ count }}</h1>
    <button pb:click="increment">+</button>
</div>

@script
<script>
    $pb.$watch('count', (now, before) => {
        console.log(`The count went from ${before} to ${now}`);
    });
</script>
@endscript
```

Inside the script, `$pb` is the component: here, the script asks to be told whenever `count` changes. A `@script` written after the root element is moved inside it when the component renders, so it still belongs to the component.

#### When a script runs

A `@script` runs **once each time its component comes onto the page**:

- when the page is loaded,
- when the user navigates to a page with the component, using `pb:navigate`,
- when a [lazy](/live-components/features/lazy-loading) component finishes loading,
- when a parent component's update brings the component in.

It does **not** run again when the component updates, so a script that sets up a listener or a chart does so once.

A `@script` written inside an `@if` runs the first time its markup comes onto the page:

```html
<div>
    <button pb:click="show_chart">Show the chart</button>

    @if(chart_shown)
        <canvas></canvas>

        @script
        <script>
            new Chart($pb.$el.querySelector('canvas'), { type: 'bar', data: {...} });
        </script>
        @endscript
    @endif
</div>
```

Values written with `{{ }}` inside a script are rendered like anywhere else in the template, and a script that has run doesn't run again because such a value changed. The code runs inside an `async` function, so you may use `await` directly.

To load a library a script needs, [push it to a stack](#pushing-to-the-layout) next to the script rather than writing a `<script src>` in the component: it is then loaded once per page, however many components need it.

### The `$pb` object

`$pb` is the component a script belongs to, what `$wire` is to Livewire. It reads and sets the component's properties and calls its actions:

```js
$pb.count           // what "count" holds
$pb.count = 5       // set it, sent with the next request
$pb.increment()     // call an action
await $pb.save()    // ...and wait for the server's answer
```

| | |
|---|---|
| `$pb.name` | What the property `name` holds |
| `$pb.name = value` | Set a property, sent with the next request |
| `$pb.action(...args)` | Call an action |
| `$pb.$get(name)` | What a property holds |
| `$pb.$set(name, value)` | Set a property and send it now |
| `$pb.$call(name, ...args)` | Call an action by name |
| `$pb.$refresh()` | Render the component again |
| `$pb.$el` | The component's root element |
| `$pb.$id` | The component's id |
| `$pb.$emit(event, data)` | Emit an event from the component |
| `$pb.$dispatch(event, data)` | The same as `$emit()` |
| `$pb.$on(event, callback)` | Listen for an event, for as long as the component is on the page |
| `$pb.$watch(name, callback)` | Be told when a property changes |

Each is covered where it belongs: [properties](/live-components/properties#accessing-properties-from-javascript), [actions](/live-components/actions#calling-actions-from-javascript) and [events](/live-components/events#using-javascript-to-interact-with-events).

### The `PyBlade` object

`PyBlade` is available to any JavaScript on the page, inside a `@script` or not: it is what `Livewire` is to Livewire. It finds components, each as its `$pb`:

```js
PyBlade.find('pb-43f55389');  // the component of that id
PyBlade.first();              // the first component on the page
PyBlade.all();                // every component on the page
PyBlade.getByName('Counter'); // every Counter component
```

`getByName()` accepts the name of the class, or its full import path when two components share a name. `PyBlade` also emits and listens for [events](/live-components/events#listening-for-events-from-global-javascript), and moves to another page with `PyBlade.navigate('/tasks/')`.
